# Spring Boot Connection Example

<!-- md-trans-meta sourceCommit=unknown translatedAt=2026-10-13T02:01:56.360Z pushedAt=2026-10-19T10:07:14.602Z -->

The dolphin plugin of openGauss implements MySQL protocol compatibility. After users enable `enable_dolphin_proto` on the database server, they can directly use the MySQL JDBC driver in a Spring Boot application to connect to the B-compatible database of openGauss, obtaining a development experience close to native MySQL.

This document describes how to use Spring Boot 3.x with the MySQL JDBC driver (mysql-connector-j) to connect to the openGauss B-compatible database, including environment preparation, project setup, connection/CRUD/transaction/batch example code, as well as precautions and known limitations.

## Environment Preparation

> The openGauss environment configuration commands in this section are the same as those in [MyBatis Connection Example](mybatis_development.html). If you have completed the environment configuration by following that document, you can skip this section.

### Preparing the Business Table Structure

1. Connect to the openGauss database using the openGauss command-line tool gsql.

   ```bash
   gsql -d postgres -p 5432 -r
   ```

2. Switch to the B database configured with MySQL protocol compatibility.

   ```sql
   \c proto_test_db
   ```

3. Create the `database` specified in the MySQL JDBC URL connection string. Under the B database, a schema in openGauss is equivalent to a database in MySQL.

   ```sql
   CREATE SCHEMA mysql_test_db;
   ```

4. Switch the schema and create the business table structure.

   ```sql
   SET current_schema to mysql_test_db;

   CREATE TABLE `user` (
       `id`   INT AUTO_INCREMENT PRIMARY KEY,
       `name` VARCHAR(50) COMMENT 'username',
       `age`  INT COMMENT 'age'
   ) DEFAULT CHARSET=utf8mb4;

   INSERT INTO `user` (`name`, `age`) VALUES
       ('Zhang San', 20),
       ('Li Si', 30),
       ('Wang Wu', 40);
   ```

5. Exit the gsql connection.

   ```sql
   \q
   ```

### Preparing the User for Connection

1. Reconnect to the openGauss database using the gsql command.

   ```bash
   gsql -d postgres -p 5432 -r
   ```

2. Create a user with the same name as the schema where the business tables reside.

   ```sql
   CREATE USER mysql_test_db WITH PASSWORD '******';
   ```

   > [!TIP]Caution
   > Do not create a user with the same name under a B database where the schema already exists; the creation will fail. The actual error is `ERROR: schema "t1" already exists`. Creating the user first and then the B database with the same name is not affected (in MySQL, the user and database namespaces are independent and can be created in any order; this order difference exists in B mode).

3. Switch to the B database configured with MySQL protocol compatibility.

   ```sql
   \c proto_test_db
   ```

4. Set the MySQL protocol authentication password for the new user.

   The dolphin plugin provides two authentication passwords: `set_native_password` corresponds to mysql_native_password in MySQL 5.7 (double SHA-1 is applied to the password), and `set_caching_sha2_password` corresponds to caching_sha2_password, the default in MySQL 8.0 (SHA-256, with the salt automatically generated by the server). During the client handshake, the server, like MySQL 8.0, always negotiates using `caching_sha2_password` as the authentication plugin; a MySQL 5.7 client falls back to mysql_native_password through authentication switching. Both passwords are written to the same field, and the one executed later overwrites the one executed earlier. The client uses the corresponding password based on the handshake negotiation result.

   ```sql
   SELECT set_native_password('mysql_test_db', '******', '');
   -- Recommended for MySQL 8.0 clients (three parameters: user, new password, old password):
   SELECT set_caching_sha2_password('mysql_test_db', '******', '');
   ```

5. Change the owner of the schema where the business tables reside.

   ```sql
   alter schema mysql_test_db owner to mysql_test_db;
   ```

6. Grant the user operation privileges on all historical tables.

   ```sql
   GRANT ALL ON ALL TABLES IN SCHEMA mysql_test_db to mysql_test_db;
   GRANT ALL ON ALL SEQUENCES IN SCHEMA mysql_test_db to mysql_test_db;
   ```

   > [!TIP]Tip
   > If a new table is created, you do not need to grant privileges to the new table again, because the owner of the schema has been changed, and the owner of the newly created table is the same as the owner of the schema.

7. Exit the gsql connection.

   ```sql
   \q
   ```

### Configuring Client Access Authentication

openGauss must be configured with client access authentication before a specified user can remotely connect to the database; otherwise, the connection fails. The configuration method is as follows:

```bash
gs_guc set -N all -I all -h "host all mysql_test_db 0.0.0.0/0 sha256"
# mysql_test_db is the database username. The omm user (the database initialization user) is not allowed for remote connections.

gs_om -t restart
```

In addition, firewall access to the MySQL protocol port (default `dolphin_server_port = 3308`) must be allowed:

```bash
firewall-cmd --zone=public --add-port=3308/tcp --permanent
firewall-cmd --reload
```

For more details, see [Configuring Client Access Authentication](https://docs.opengauss.org/en/docs/latest/database_administration_guide/configuring_client_access_authentication.html).

## Project Setup

### Creating a Maven Project

Create a standard Maven project (Spring Boot 3.x requires JDK 17+). The directory structure is as follows:

```
springboot-connect-opengauss-b
├── pom.xml
└── src
    ├── main
    │   ├── java/org/opengauss/smoke
    │   │   └── SmokeApplication.java   # Startup class
    │   └── resources
    │       └── application.yml         # Data source configuration
    └── test
        └── java/org/opengauss/cases/   # Test cases (see the examples repository)
```

### Adding Dependencies

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.16</version>
</parent>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-jdbc</artifactId>
    </dependency>
    <dependency>
        <groupId>com.mysql</groupId>
        <artifactId>mysql-connector-j</artifactId>
    </dependency>
</dependencies>
```

> [!NOTE]Note
> MySQL driver 8.0.28 and earlier use the legacy coordinates `mysql:mysql-connector-java`; starting from 8.0.31, the new coordinates `com.mysql:mysql-connector-j` are used. The Spring Boot 3.x BOM automatically manages the version of the new coordinates (Boot 3.5.16 resolves 9.7.0 by default), so no explicit version is required. As verified by testing, **all versions from 8.0.28 to 26.7.0 work correctly for basic CRUD, transaction, batch, and type mapping scenarios in openGauss B-compatible mode**.

### Preparing the Configuration File

Example of the data source configuration in `application.yml`. Note that **the port is the dolphin protocol port (`dolphin_server_port`, default 3308), not the native openGauss port 5432**:

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3308/mysql_test_db?useSSL=false&serverTimezone=UTC&characterEncoding=utf-8
    username: mysql_test_db
    password: '******'
    driver-class-name: com.mysql.cj.jdbc.Driver
    hikari:
      maximum-pool-size: 10
```

## Sample Code

### Connection and Query

```java
// Directly inject JdbcTemplate in the Spring container.
@Autowired
private JdbcTemplate jdbcTemplate;

// Query: mysql_test_db in the URL is the schema under the B database.
List<Map<String, Object>> users = jdbcTemplate.queryForList("SELECT * FROM `user`");

// Metadata: productName = MySQL, productVersion = 8.0.28-dophin-server
try (Connection c = jdbcTemplate.getDataSource().getConnection()) {
    DatabaseMetaData md = c.getMetaData();
    System.out.println(md.getDatabaseProductName() + " / " + md.getDatabaseProductVersion());
}
```

### Insert, Update, and Delete

```java
jdbcTemplate.update("INSERT INTO `user` (name, age) VALUES (?, ?)", "Zhao Liu", 28);
jdbcTemplate.update("UPDATE `user` SET age = ? WHERE name = ?", 29, "Zhao Liu");
jdbcTemplate.update("DELETE FROM `user` WHERE name = ?", "Zhao Liu");
```

### Transaction

```java
// Programmatic transaction (TransactionTemplate)
@Autowired
private TransactionTemplate txTemplate;

txTemplate.execute(status -> {
    jdbcTemplate.update("INSERT INTO `user` (name, age) VALUES (?, ?)", "tx_a", 1);
    jdbcTemplate.update("INSERT INTO `user` (name, age) VALUES (?, ?)", "tx_b", 2);
    if (rollback) {
        status.setRollbackOnly(); // Roll back both together
    }
    return null;
});
```

### Batch Write

For batch write, it is recommended to enable `rewriteBatchedStatements=true`. In tests, the time for writing 500 rows dropped from about 1020 ms to about 59 ms (an approximately 17x speedup). Two approaches are available:

```java
// Approach 1: JdbcTemplate.batchUpdate
jdbcTemplate.batchUpdate("INSERT INTO `user` (name, age) VALUES (?, ?)", batchArgs);

// Approach 2: Use PreparedStatement after enabling batch rewrite through the connection parameter.
String url = "jdbc:mysql://127.0.0.1:3308/mysql_test_db?useSSL=false"
        + "&serverTimezone=UTC&rewriteBatchedStatements=true";
try (Connection c = DriverManager.getConnection(url, "mysql_test_db", "******")) {
    try (PreparedStatement ps = c.prepareStatement("INSERT INTO `user` (name, age) VALUES (?, ?)")) {
        for (int i = 0; i < 1000; i++) {
            ps.setString(1, "batch_" + i);
            ps.setInt(2, i);
            ps.addBatch();
        }
        int[] counts = ps.executeBatch();
    }
}
```

## Notes and Known Limitations

1. **Database object naming**: Table names and column names use backticks `` ` `` (a MySQL convention; `user` is a MySQL reserved word and must be enclosed in backticks);
2. **Port**: The MySQL protocol uses `dolphin_server_port` (default 3308). Connecting to the native port 5432 reports `Communications link failure`;
3. **Driver version range**: Matrix testing across 8 driver versions (8.0.28 to 26.7.0) shows consistent behavior in basic scenarios. Version 8.0.28 and earlier use the old Maven coordinates `mysql:mysql-connector-java`;
4. **Zero dates**: Storage of zero dates (`0000-00-00`) is controlled by `no_zero_date` in `dolphin.sql_mode`: it is enabled by default, and inserting reports `date/time field value out of range`; after removing it from sql_mode, zero dates can be stored normally. When a table contains zero dates, all three `zeroDateTimeBehavior` settings take effect as tested: `convertToNull` reads them as null, `exception` throws `Zero date value prohibited` on read, and `round` reads them as `0001-01-01`, consistent with MySQL semantics;
5. **Isolation level**: Setting SERIALIZABLE is mapped by the server to REPEATABLE_READ (`getTransactionIsolation` reads back 4);
6. **JDBC metadata APIs and table name case sensitivity**: Views such as TABLES, PARAMETERS, and KEYWORDS under `information_schema` all exist (queryable in lowercase), but under the default configuration (`dolphin.lower_case_table_names=0`) they are case-sensitive. The driver sends uppercase TABLES following MySQL conventions and reports `relation "information_schema.TABLES" does not exist`, causing metadata probing by APIs such as `DatabaseMetaData.getTables` and ORM frameworks to fail. **Solution: set `dolphin.lower_case_table_names` to 1** -- append `dolphin.lower_case_table_names = 1` to postgresql.conf and restart for global effect (session-level `SET` affects only the current session; application/driver scenarios require persistent configuration). After the setting, uppercase TABLES is queryable and `DatabaseMetaData.getTables` works normally as tested;
7. **Cursors and stored procedures**: The previously recorded stored procedure call error `information_schema.PARAMETERS does not exist` is actually caused by case sensitivity under the default configuration -- the PARAMETERS view exists and is queryable in lowercase; after setting `dolphin.lower_case_table_names=1`, it is queryable in uppercase (see item 6). The protocol layer provides limited support for cursors and stored procedures; rewrite such scenarios as ordinary SQL or batch processing;
8. **Type mapping and JDBC parameters**: TINYINT(1)/BIT(1) is mapped to Boolean by default; DATETIME is mapped to LocalDateTime, and TIMESTAMP is mapped to Timestamp. Of the 6 JDBC parameters listed in the official protocol compatibility documentation, testing shows that `tinyInt1isBit`, `useOldAliasMetadataBehavior`, and `allowMultiQueries` take effect; `transformedBitIsBoolean` (both settings map to Boolean on the Java side), `useaffectedrows` (always returns the number of rows found), and `zeroDateTimeBehavior` (all three settings take effect, see item 4) behave as documented.
